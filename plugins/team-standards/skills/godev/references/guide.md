# Go Style 主指南（Guide · Canonical + Normative）

来源：https://google.github.io/styleguide/go/guide

本文档为规范性 + 典范性文档，是整个 Go 风格指南的根基。Normative（决策）和 Idiomatic（最佳实践）都从属于它。

## 风格原则（Style Principles）

可读代码按以下属性从高到低排序：

1. **清晰（Clarity）**：代码的目的和理由对读者透明。
2. **简洁（Simplicity）**：用最简单的方式达成目标。
3. **简练（Concision）**：信号噪声比高。
4. **可维护（Maintainability）**：代码容易修改。
5. **一致（Consistency）**：与更广的 Google 代码库保持一致。

### 清晰

清晰面向**读者**而非作者。代码应"易读"优先于"易写"。

清晰有两个面：

- **代码在做什么**（`What`）：必要时用更具描述性的命名、加注释、用空白和注释切分代码、拆函数让模块化。
- **代码为什么这样做**（`Why`）：当含义无法靠命名传达时，加注释解释"为什么"。特别注意：语言陷阱（如闭包捕获循环变量）、业务逻辑（区分真实用户与冒名顶替）、性能取舍、复杂 API。

警惕"过度注释"反而模糊代码：让代码自描述（命名本身就是说明），注释解释"为什么"而不是"在做什么"。

Google 代码库风格高度统一。**与众不同的模式通常是有意为之**（常为性能），看到时仔细看，不要轻易"统一"掉。

标准库的好例子：`package sort` 的维护者注释、`example_search_test.go` 的可运行示例（既出现在 godoc 也作为测试运行）、`strings.Cut`（四行代码，调用点清晰且正确）。

### 简洁

代码要简单——对使用者、阅读者、维护者都简单。

简单代码的特征：

- 自上而下易读
- 不假设你已知道它做什么
- 不假设你能记住前面的所有代码
- 没有不必要的抽象层
- 命名不刻意突出平庸的事
- 值和决策的传播对读者透明
- 注释解释"为什么"而不是"在做什么"，避免未来偏离
- 文档独立可读
- 有有用的错误和测试失败信息
- 常与"clever"代码互斥

API 使用简洁和代码本身简洁可能有冲突：有时让实现复杂一点换 API 易用，有时让调用方多写一点换实现简单。当复杂性必要时**有意识地引入**（性能、多客户），并配文档、测试、示例。

"最小机制（Least mechanism）"：能用核心语言构造（channel、slice、map、循环、struct）就用；不行用标准库（HTTP client、template engine）；都不行才考虑 Google 核心库或新依赖。

反例：测试时用 `flag.Set` 覆盖值，不如直接赋给变量；用 `map[string]bool` 做集合检查就够，不要引 set 库。

### 简练

高信号噪声比。阻碍信号的因素：

- 重复代码
- 多余语法
- 不透明命名
- 不必要抽象
- 空白

重复代码会迫使读者"视觉对比"找差异。table-driven 测试是把共性抽出来、把差异摆出来的好范式。

考虑多种代码组织方式时，优先选"让重要细节最显眼"的那种。

```go
// 常见模式，读者一眼懂
if err := doSomething(); err != nil {
    // ...
}
```

```go
// 看似一样实际相反，必要时用注释"放大信号"
if err := doSomething(); err == nil { // if NO error
    // ...
}
```

### 可维护

代码被改的次数远多于写的次数。

可维护代码：

- 未来程序员容易正确修改
- API 结构允许优雅成长
- 抽象对应问题的结构而非代码的结构
- 不必要耦合、不包含未用特性
- 有完整测试套件，测试失败信息明确可执行

抽象（接口、类型）会移除上下文信息——确保它们提供足够价值。编辑器和 IDE 能从具体类型跳到方法定义并显示文档，接口只能跳到接口定义。接口是强工具，但有代价。

避免把重要细节藏在容易忽略的地方：

```go
// Bad: 用 = 不用 := 完全改变这行
if user, err = db.UserByID(userID); err != nil {
    // ...
}

// Bad: 中间的 ! 很容易漏
leap := (year%4 == 0) && (!(year%100 == 0) || (year%400 == 0))
```

```go
// Good: 显式 + 错误
u, err := db.UserByID(userID)
if err != nil {
    return fmt.Errorf("invalid origin user: %s", err)
}
user = u

// Good: 拆分 + 注释
// Gregorian leap years aren't just year%4 == 0.
var (
    leap4   = year%4 == 0
    leap100 = year%100 == 0
    leap400 = year%400 == 0
)
leap := leap4 && (!leap100 || leap400)
```

可预测的命名：包用户和维护者应能在给定上下文预测变量/方法/函数的命名。同概念的函数参数和 receiver 名字应一致。

最小化依赖：依赖越少，能影响行为的代码越少。避免依赖未文档化或内部行为。

设计/写代码时考虑未来演化：让方案更易演化（即使稍复杂）通常是好交易。

### 一致

代码应在更广代码库、同团队同包、甚至同文件内看起来、感觉上、行为上都一致。

一致不凌驾于以上原则，但平局时倾向一致。

包内一致性最直接：同包内同一问题不要多种解法。但包内一致性也不应凌驾于已记录的风格原则或全局一致性。

## 核心准则（Core Guidelines）

所有 Go 代码预期遵循的高频要点。期望在学习可读性之前已掌握：

### 格式（Formatting）

所有 Go 源文件必须符合 `gofmt` 输出格式。Google 代码库由预提交检查强制。生成代码也应格式化（如 `format.Source`），因为它在 Code Search 中可浏览。

**团队加码**：必须同时跑 `goimports` 和 `golangci-lint`（开启 `errcheck` / `govet` / `staticcheck`）。

### MixedCaps

多词命名用 `MixedCaps` 或 `mixedCaps`（camel case），不用下划线。

即使与其他语言约定冲突也如此。常量导出 `MaxLength`（不是 `MAX_LENGTH`），非导出 `maxLength`（不是 `max_length`）。

局部变量按"非导出"决定首字母大小写。

### 行长（Line length）

Go 无固定行宽。觉得太长**优先重构拆分**，而不是断行。已经够短就允许保留长行。

不要在以下位置拆行：

- 缩进变化处（函数声明、条件分支）
- 长字符串（URL）

### 命名（Naming）

命名是艺术不是科学。Go 中命名一般比其他语言短，但通用准则仍适用。命名应：

- 用起来不显得重复
- 考虑上下文
- 不重复已清晰的概念

更多命名细节见 `decisions.md#naming`。

### 局部一致性（Local consistency）

风格指南没规定时，作者可自由选风格，除非近距离（通常同文件或同包，有时同团队或项目目录）已有统一定调。

**有效**的局部风格选择：

- 错误打印用 `%s` 或 `%v`
- 用 buffered channel 代替 mutex

**无效**的局部风格选择：

- 行宽限制
- assertion-based 测试库

如果局部风格与风格指南不符但影响限于一个文件，code review 会指出但 CL 范围内不修；开 bug 跟踪修复。

如果改动让已有的风格偏离**更糟**（扩展到更多 API 表面、更多文件、引入实际 bug），局部一致性就不再是新代码违反风格指南的借口。这种情况作者应：(1) 在同一个 CL 内清理既有代码；(2) 在当前 CL 前先重构；(3) 找至少不加剧问题的替代方案。
