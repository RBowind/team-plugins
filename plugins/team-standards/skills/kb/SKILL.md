# 知识库（kb）

知识库回答的是**以后还会被再问一次的问题**，而提问的人不是当初写代码的人。

三条判据同时成立才进知识库：涉及多个服务或团队、未来会被独立查询、有可靠证据支撑。代码仓库记实现，工作项记过程，运行手册记操作步骤，知识库记结论——所以页面得让不认识作者、不知道上下文的人直接拿到答案。

由此推出后面所有规则：证据决定页面能不能发布，唯一归属决定它会不会自相矛盾，状态决定别人敢不敢拿它当事实用。

## 三种入口

| 你在做什么 | 走哪里 |
|---|---|
| 开工前查、回答别人的问题 | 三·1 默认使用稳定知识 |
| 开发、讨论、复盘、迁移中形成了一条结论 | 一 → 二：发现与判断 → 验证与发布 |
| 定期体检，或用户说"巡检知识库" | `/team-standards:kb-health` |

## 一、发现与判断

### 1. 判断是否进入知识流程

出现下面任一情况，说明有跨边界的东西变了：

- 涉及多个服务或团队；
- 业务流程、状态流转或用户可观察行为变了；
- 服务边界、接口契约或责任归属变了；
- 产生了要长期保留的技术决策或事故结论。

判据是"**谁会再问一次**"。只有本服务的开发者会问、答案又躺在代码里，那代码旁边就是它最好的位置：纯服务内部实现留在代码仓库，临时排查记录留在任务记录，一次性操作说明留在运行手册。这三样进知识库只会稀释检索结果。

### 2. 检索已有知识

先读 KB 根的 `index.md`，再按五个角度定位：

1. 业务领域；
2. 跨服务流程；
3. 共享实体；
4. 服务边界；
5. 长期决策。

命中后三种处理：页面仍然正确 → 直接用；需要变化 → 改原页面；没有合适页面 → 再判是否真的需要新建。一条知识只保留一个正式归属，其余位置改成引用——同一件事写两遍，读者不知道该信哪一份，维护者也迟早只更新其中一份。

### 3. 记录知识缺口

工作需要一个长期有效的跨服务答案、而知识库里没有时，把它记在当前工作项里（techspec 的 `*.follow-ups.md`、contract 的 Follow-ups 段；没有工作项产物时写进 PR 描述或 issue）：

- 缺什么答案；
- 涉及哪些服务或角色；
- 预期从哪里获得证据。

缺口是待回答的问题，不阻塞开发，也不建页面。功能收尾时每个缺口都要落地：形成页面，或者说明它为什么不归知识库。

## 二、验证与发布

### 1. 捕获候选结论

开发、讨论、事故复盘、旧文档迁移中，先把可能值得沉淀的结论记成候选。进入知识库的条件是三条同时成立：跨服务或跨团队、未来可能被独立查询、已有证据支持而不只是个人判断。

旧文档只作迁移来源，不自动证明内容今天仍然正确——迁移过来的每条结论都要重新对一次当前证据。

### 2. 查重并选择归属

写作前再查一次重：已有页面能承载 → 更新原页面；已有页面只需引用 → 加链接；没有归属 → 按流程、实体、服务、集成或决策新建页面（判据见 `references/canon.md`）。

项目名本身不构成归属。为一个项目专门建索引页，通常只是在知识库里复制一份任务清单；只有它确实沉淀出一条可独立查询的业务流程时才建。

### 3. 核对证据

页面里区分三类证据，各自标明来源：

- **意图**：正式产品需求、业务规则或设计决策；
- **当前行为**：已合并代码和服务文档；
- **验证过的例外**：事故调查、线上验证或可靠测试结果。

证据互相矛盾时，把差异原样记录下来，指明哪一方在哪个边界上成立，交给责任方确认。替读者拍板会把一条待确认的冲突伪装成结论。

### 4. 发布知识

按成熟程度定状态：

- **草稿**：已有证据，边界或事实仍待确认；
- **审核中**：跨服务事实有争议，等责任方确认；
- **稳定**：证据完整、边界清晰，可进默认检索。

发布前跑一次机械校验并自检来源、责任边界和相关链接：

```bash
python <本 skill 目录>/scripts/kb_lint.py --root <KB 根>
```

新增或删除页面时，同步更新 `index.md`（导航）和入链（知识图谱）：删除页面时把指向它的链接一并处理，留下断链比留下旧页更糟。要出图时走 tech-diagram-design，图与页面同源更新。

功能结束前回头确认：本次的每个知识缺口都已有结论，谱系上和它就差一个页面。

### 5. 影响他人的动作先确认

动手前把候选和理由报给用户或页面的 `owner`，等确认，这三类动作都改变别人手上的东西：

- **删除页面**（连带清理它的入链和导航条目）；
- **改 `owner` 或 `services`**；
- **把 `stable` 降级**。

机械修复可以直接做，它们让页面回到本该有的状态：补断链、同步 `index.md`、修 frontmatter 格式、更新自己刚核对过的 `verified_at`。

判断标准是这个动作做错时谁受损、他什么时候才发现：降级一条 `stable` 会让它立刻掉出所有人的默认检索，删一页会让另一个团队正用着的答案消失，而补一条断链谁都不会因此失去什么。合并重复页时优先"保留一个归属、其余改为引用"，这个方向可逆；确需删页则先确认。

## 三、使用与维护

### 1. 默认使用稳定知识

日常查询和新功能开发默认只加载 `status: stable` 的页面。草稿和审核中页面用来调查未解决的问题，引用时必须带上状态；它们读起来和稳定页一样像结论，直接传播就等于把未确认的判断当事实用。

### 2. 建立反馈闭环

知识库在使用中持续修正：

- 查不到本应存在的答案 → 记知识缺口；
- 页面与当前证据不一致 → 重新验证并更新；
- 多个页面重复解释同一事实 → 保留一个正式归属，其余改为引用（要动到删除、降级或 owner，先按二·5 报候选等确认）；
- 形成新结论 → 回到"判断 → 查重 → 验证 → 发布"。

### 3. 定期检查健康度

跑 `/team-standards:kb-health`，或在收尾时代跑一次 `kb_lint.py`。检查项：没有入口的孤立页面、指向不存在内容的断链、长期未核对的页面、与当前代码或业务规则可能不一致的内容。

自动工具只出候选名单，判断仍需回到证据。错误、重复、已被取代的页面直接删除，历史交给版本控制——永久归档区只会让下一个读者多绕一圈。

## 输出位置

KB 根跟随宿主 repo 的既有约定（`docs/kb/`、`docs/knowledge/`、`wiki/` 都算）；没有约定时新建 `docs/kb/`。页面按归属分类放子目录：

```text
docs/kb/
├── index.md          # 导航：分类目录 + 每页一行摘要
├── flows/            # 跨服务流程、状态流转
├── entities/         # 共享实体、枚举、生命周期
├── services/         # 服务职责与边界
├── integrations/     # 接口契约、调用方向、责任方
└── decisions/        # 长期技术决策与事故结论
```

文件名用英文 kebab-case，正文中文。命名描述问题域而不是项目名：`refund-responsibility.md` 会在三年后仍被搜到，`proj-x-refund.md` 不会。
