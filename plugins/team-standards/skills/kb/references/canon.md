kind: integration          # flow | entity | service | integration | decision
status: stable             # draft | review | stable

services: [order, payment]  # 涉及的服务，供检索和巡检使用

## 证据

正文第一段是一句话结论：这条知识回答什么问题、答案是什么。读者读完这一段就该能走人，后面的骨架是给要深究的人准备。

## 五类归属

| kind | 收什么 | 判断问句 |
|---|---|---|
| `flows/` | 跨服务业务流程、状态流转、用户可观察行为的链路 | 这条流程有几个服务参与？换掉其中一个服务，描述还成立吗？ |
| `entities/` | 跨服务共享的实体、字段语义、枚举、生命周期 | 几个服务读写同一个实体？字段含义在两边有分歧吗？ |
| `services/` | 单个服务的职责、边界、拥有的实体与接口、依赖 | 这个服务对什么负责、对什么不负责？边界在哪里？ |
| `integrations/` | 服务之间的接口契约、调用方向、错误与重试语义、责任方 | 两个服务之间约定的是什么？谁在失败时兜底？ |
| `decisions/` | 长期技术决策、事故结论、被放弃的方案 | 这个决定三年后还有人需要知道为什么吗？ |

归属的判断顺序是：先看它描述的是**动作链路**（flows）、**数据结构**（entities）、**一方职责**（services）、**两方约定**（integrations），还是**为什么这样选**（decisions）。一条知识只落一个 kind，跨类的内容按主要读者放，其余位置放链接。

不为单个项目建索引页。项目的任务清单和进度属于工作项；只有当项目沉淀出一条可独立查询的业务流程时，它才以流程页的形式进知识库。

## 各 kind 的骨架

**flows**：触发 → 参与服务与各自动作 → 终态；状态流转用表格或 Mermaid 状态图；失败分支单独写。

**entities**：字段与语义 → 枚举与取值 → 生命周期（谁创建、谁变更、谁销毁）→ 归属服务。

**services**：职责 → 边界（明确不负责什么）→ 拥有的实体与对外接口 → 依赖方向。

**integrations**：接口契约 → 调用方向与触发时机 → 错误与重试语义 → 责任方与兜底方。

**decisions**：背景一句话 → 决定 → 理由 → 影响面 → 放弃的方案及其代价 → 何时该重看。

## 证据

三类证据都标来源，来源要能点开或被再次定位：

- **意图**：正式产品需求、业务规则、设计决策。写文档名加定位（章节、条款号），或直接链接。
- **当前行为**：已合并代码和服务文档。写仓库、路径、符号或接口名。
- **验证过的例外**：事故调查、线上验证、可靠测试结果。写结论加发生时间或验证方式。

用户确认是最高优先级证据，可证明新的目标设计；代码和文档只证明当前实现事实，证明不了"以后应该怎样"。

证据不足以支撑结论时，要么补证据，要么把结论降级为草稿并写清待确认的边界。证据冲突时原样记录双方与各自成立的边界，不擅自选边；分歧涉及责任归属时把状态置为审核中，等责任方确认。

## 状态

| status | 含义 | 谁能拿它当事实 |
|---|---|---|
| `draft` | 已有证据，边界或事实仍待确认 | 不能。可以引用，必须带状态 |
| `review` | 跨服务事实有争议，等责任方确认 | 不能。可以引用，必须带状态 |
| `stable` | 证据完整、边界清晰 | 可以，进默认检索 |

升降级都允许：证据补齐、边界确认后 draft / review → stable；发现证据失效或边界变化时 stable → draft，并在 `verified_at` 之外不再加任何过期说明字段。`verified_at` 只在对着证据核对过内容之后更新。

删除：错误、重复、已被取代的页面可以删，历史交给版本控制，不建归档区和墓碑。删页面时同步清理 `index.md` 条目和所有指向它的链接。删除页面、改 `owner` 或 `services`、把 `stable` 降级这三类动作先报候选等确认（见 `SKILL.md` 二·5）；补断链、同步导航这类机械修复直接做。

## 导航与图谱

- **导航**：`index.md` 按 kind 分节，每页一行摘要。摘要写这条知识回答什么问题，不写"某某文档"。新增、重命名、删除页面时同步更新。
- **图谱**：页面间用相对 markdown 链接互指，`## 相关内容` 里每条写一句为什么相关。链接的目标必须存在；写链接时顺手确认被引用页面仍然支撑你的说法。
- 链接一律用相对路径（GitHub 上可点），不用本 repo 私有约定之外的 wiki 双链语法。
- 需要图时走 tech-diagram-design，图与页面同源更新；图里的实体、字段、接口以页面正文为准。

## 发布前校验清单

1. `python <kb skill 目录>/scripts/kb_lint.py --root <KB 根>` 无 error（frontmatter、状态取值、断链、导航一致）。
2. 三条判据同时成立：跨服务或跨团队、会被独立查询、有证据支撑。
3. 归属唯一：同一事实没有第二处正式解释；跨类内容其余位置只放引用。
4. 证据三类各自标了来源，冲突已记录而非已裁决。
5. `status` 与证据成熟度相符，`verified_at` 是本次核对日期。
6. `owner` 和 `services` 与正文一致。
7. `index.md` 与入链已同步；删除的页面没有留下断链。
8. 本次若删除过页面、改过 `owner` 或 `services`、把 `stable` 降过级，逐条有用户或责任方的确认记录；没有确认的只作为候选写进交付说明。
9. 需要独立评审时跑 `<plugin 根>/agents/kb-reviewer.md`，它只判不改。

## 语言与命名

- 正文中文，工程语言，结论先行。
- 文件名英文 kebab-case，描述问题域而非项目名。
- 一句话能说清的结论放在第一段；不写"本文档旨在""综上所述"这类填充。
- 术语第一次出现时展开，与宿主 repo 和团队既有术语表保持一致。
- 不写 AI 套话（赋能、抓手、闭环、范式、打通、底座、全链路、一站式、沉淀为……）。
