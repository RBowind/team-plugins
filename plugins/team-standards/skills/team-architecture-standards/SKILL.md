# 团队架构规范

## 分层

每个业务领域一个包：`internal/<domain>/`，包内按职责分文件。

- **handler**：接收请求、参数校验、调 service、组装响应。不写业务逻辑，不直接碰数据层。
- **service**：业务逻辑与业务验证。不 import `net/http`，不感知请求、响应对象。
- **repository**：数据访问，封装 SQL 与行到结构的转换。不做业务判断。

依赖单向：handler → service → repository。禁止反向与跨层：service 不 import handler，repository 不 import service。

模块间调用只走对方包的公开接口，不 import 对方的内部类型。一个用例横跨多个领域时，编排代码放调用方所在包或专门的应用层包，领域包之间不互相依赖内部实现。

## 接口与实现

- 消费者定义接口，生产者返回具体类型。service 的依赖用构造函数注入，不在函数内 new。
- 不为「将来可能」预抽接口；需要替换实现（测试、多存储）时，由消费方定义它需要的那部分接口。
- repository 无状态，持有连接池；单个操作自动提交。
- 跨 repository 的写操作在 service 层用事务协调，由 service 管理提交与回滚。

## DTO 与错误

- service 对外返回视图结构（DTO），不暴露 repository 的行结构；API 层不知道表结构。
- 业务错误定义在 service 层，用哨兵错误或自定义类型，保证 `errors.Is` 可判等。
- 错误逐层转换：repository 原样返回技术错误（必要时 `%w` 包装）；service 定义业务错误；handler 统一映射——业务错误映射到 4xx，未知错误返回 500 且记日志，不回传内部细节。

## 配置

- 环境变量在启动时校验并装进配置结构，缺失或非法立即退出；不运行到一半才发现配置错误。

## 改动范围

- 只动任务声明的模块和文件；发现「顺手改一下别的模块更好」时停下，把建议单独说。
- 跨模块、跨服务的改动先声明影响面，确认后再动。
- 公共代码（共享库、基类、公共工具）的修改视为跨模块改动，从严处理。

## 数据模型

- 表结构、字段、索引变更必须先提出变更方案，不许在写代码时顺手加字段。
- 字段只加不改不删：改名、删字段、改类型要走迁移方案，明确兼容旧数据。
- 迁移脚本和代码在同一个 PR 里，迁移可重跑、可回滚。

## 演进与选型

- 新功能优先复用现有的模式、中间件、公共库，不为一处需求引入第二套同类设施。
- 引入新的中间件、框架、存储属于技术选型变更：写一页纸说明（解决什么问题、替代什么、代价是什么），进 decision-log 后再动手。
- 大改动（新服务、新模块、接口契约变更）先按 techspec skill 写规格，评审通过再写代码。

## 一票否决线

- 单点无降级的基础设施变更（如换网关、换数据库），没有回滚方案不动手。
- 影响计费、权限模型的结构性改动，必须人拍板，AI 只出方案。
