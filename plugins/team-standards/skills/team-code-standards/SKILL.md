# 团队编码规范

## 命名

- 名字直接说意图，不用团队内没人懂的自造缩写。
- 布尔值用 is / has / can / should 开头；函数名动词开头，如 `parseOrder`、`retryWithBackoff`。
- 一个名字在作用域内只有一个意思，不复用变量名装不同含义的东西。
- Go 的命名细则（MixedCaps、包名、receiver、getter）见 godev skill。

## 函数与结构

- 一个函数只做一件事；超过约 50 行或嵌套超过三层，先拆再写。
- 卫语句提前返回，主逻辑不包在深层 if-else 里。
- 新代码放项目现有的目录和模式里，不另起炉灶；新增目录先说明理由。

## 注释与日志

- 注释只写「为什么」（业务背景、坑、约束），不复述代码在做什么；不留死代码。
- 入口、出口、失败路径记日志；用项目统一的日志工具，不裸 print / fmt.Println。
- 日志与报错不打敏感信息（token、密码、证件号、手机号明文）。

## 错误处理

- 不吞错误：不空 catch、不 `_ = err` 带过；处理、返回、记日志，三选一。
- 错误走项目统一的错误通道（错误码 / error 类型 / 中间件），不各造一套。
- 对外报错不给内部细节（堆栈、SQL、文件路径）。

## 依赖

- 加新依赖前先搜项目里有没有同功能的；重复引依赖和重复造轮子都算问题。
- 改动说明里写一行：引了什么、干什么用。

## 格式

- 格式交给工具：改完跑项目 lint / format，不手调空格缩进。
- lint 报的错必须修；确需忽略的在改动说明里写明原因，不留裸忽略注释。

## 安全红线

本节是硬边界，与质量要求不同：违反任何一条立即停下向人报告，不「先跑通再说」。拿不准是不是安全问题的，当安全问题处理，停下来问，不猜。

### 凭据与配置

- 密钥、token、连接串不硬编码，走环境变量或配置中心。
- 提交前确认 .gitignore 覆盖 .env、密钥文件、证书；看到凭据类文件要进 git，立即停下。
- 历史代码里的硬编码凭据不当作正常现状沿用，发现即报告。

### 注入

- 一切外部输入（HTTP 参数、header、文件、消息队列、第三方回调）都不可信。
- SQL 一律参数化查询，不拼字符串。
- 命令行、文件路径、URL 拼接走白名单校验，不直接拼用户输入。
- 渲染输出转义防 XSS；反序列化不接不可信来源。
- Go：用户输入不拼进 `os/exec` 命令字符串，参数用数组传递，不走 `sh -c` / `cmd /c` 拼接。
- Go：渲染 HTML 用 `html/template`（自动转义），不用 `text/template` 渲染用户内容。
- Go：用户输入进文件路径先 `filepath.Clean`，再校验白名单前缀，防路径穿越。

### 权限与敏感操作

- 涉及登录态、权限的代码默认最小权限：先拒绝，显式放行。
- 金额、权限、批量删除这类操作，只写实现，不擅自「顺手」简化校验逻辑。
- 敏感操作必须留审计日志：谁、何时、对什么做了什么。

### 数据

- 日志、报错信息、返回体里不出现敏感数据明文；手机号、证件号要脱敏。
- 不把生产数据拷到测试环境或本地；测试用造的假数据。

### 供应链

- 依赖只从官方源安装，不装停更、来历不明的包。
- 锁文件必提交（go.sum / package-lock.json）；Go 禁止 replace 指向来路不明的模块。
- 生成密钥、随机数用 `crypto/rand`，不用 `math/rand`。
- 出网请求走项目统一封装，有超时、有错误处理；不让用户输入直接决定请求目标。
