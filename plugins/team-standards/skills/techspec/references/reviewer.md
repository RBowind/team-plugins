# Techspec 独立检查器

在 draft 或 reshape 后运行一次独立审查。reviewer 不是第二个作者：它不修改 techspec、evidence、PRD、源文档或代码；唯一写权限是对应的 follow-ups 文件。

## 输入包

1. 目标 techspec：单文件形态给一个 spec 文件；文档集形态给同一工作区中的入口文件 + 全部详情文件，并提供入口的相对路径。
2. `references/techspec-canon.md`
3. PRD 或源文档（被重塑或对账的外部源文件，PRD 之外：别仓 schema/DDL、设计文档、已有 spec）：重塑时给源文档做对账；从 PRD 起草时给 PRD；没有源文档则跳过 faithfulness 对账
4. 同基名 `.evidence.md`，如存在（文档集形态下挂在入口文件同基名）
5. 同基名 `.follow-ups.md`，如存在（文档集形态下挂在入口文件同基名）

文档集形态由主 agent 在输入包里说明，并把整套文件都提供。详情文件须可由入口的相对链接解析到同一工作区。不要提供写作过程。reviewer 以零先验、对抗性视角审查最终产物。

## 证据核验

- `来源：用户确认` 是最高优先级依据。无需外部核验，只检查 evidence 与 techspec 是否一致。
- 代码、迁移、配置、ADR、设计文档和 ticket 等外部来源必须打开核验。路径或链接不可访问、不存在、已变化，或内容无法支持该事实时，报 🔴。
- 代码、迁移和配置只能证明当前实现事实，不能单独证明新的设计选择。
- 用户确认的新目标设计可以不同于当前代码；这不是冲突。
- 两个非用户确认来源互相冲突，或 ADR / 设计文档 / ticket 与 PRD / 源文档冲突时，报 🔴，由用户决定。
- 用户确认与其他来源冲突时，以用户确认的当前决定为准，不报 finding。

## 检查内容

按 canon 审查，优先定位证据再裁决。每个 finding 必须有行号和规则来源。

- **A. Fabrication**：是否把无依据的字段、enum、约束、索引、机制或接口细节写成事实？
- **B. Faithfulness**：是否遗漏或改坏当前有效的字段、约束、状态机、主流程或设计选择？不要将 rename 历史、drift、排除列清单或对账叙事当作必须保留的决策。
- **C. Canon**：五段结构、占位符、历史内容、DDL 摘要、接口范围和图示规则是否符合 canon？§3 必须含本表所有已确认 enum 值；章节顺序与语义与 canon 固定结构一致，标题语言遵循输出语言；§2 不重述 §3/§4/§5 的实现细节（字段、enum、状态机转换、流程步骤、接口契约），需要时引用对应章节。**形态感知**：单文件形态五段都得有内容；文档集形态入口文件的 §3/§5 可导航式（一行链接 + 概要），不算缺内容——前提是相对链接指向同一工作区、随输入包提供的详情文件，且内容对得上（对不上见 D；缺失见链接完整性）。入口文件仍必含全部 5 个 section title。
- **D. Consistency**：数据模型、ER 图、流程图、状态图和接口契约中的字段、enum、约束和行为是否一致？**文档集形态加跨文件一致性**：入口文件端点清单 ↔ 详情接口文件（端点、HTTP 方法、路径对得上）；入口文件状态 enum、ER 概览 ↔ 详情表结构文件（enum 值、表关系对得上）；入口文件鸟瞰流程 ↔ 详情流程文件（参与方、关键步骤对得上）。对不上 → 有明确权威（以详情文件为准）→ 🟡 把入口对齐过去；两边都权威且冲突 → 🔴 交用户。
- **链接完整性**（文档集形态）：入口文件每条"见 X 文件"链接，按相对路径打开核验：目标在同一工作区、随输入包提供、文件存在，且链接内容支持入口概要。外部 URL、其他仓库文件或仅被附在输入包中的无关文件，不能当作详情文件替代 section 内容；按指针规则处理。链接断了或不属于文档集 → 🔴（需用户决定补文件、调整内容或删链接）；概要对不上 → 🟡。这条是文档集形态下"文件内自洽"的整套级替代。
- **软性检查**：信息密度、实现充分性、零先验读者可读性和自然工程语言。优先调用 humanizer；humanizer 不可用时自行检查填充词、重复和过度书面语。**可读性/分组**（🟢）：按 canon 可读性/分组规则——一段连续文字或扁平列表有好几个没被结构隔开的关注点 → 🟢；单一内聚种类的扁平列表（表字段、enum 取值、端点参数）不报。判定只问是/否（“是不是好几个没隔开的关注点挤一起”），不数行数、不数关注点。对 🟢 可读性项不连续重复报同一类（一段报一条）。

## Follow-ups 写入边界

reviewer 可创建、增加、删除、去重或做不改变含义的措辞整理，仅限目标 spec 的 `.follow-ups.md`。

- 仅将“已确认主流程确实需要、但不影响主流程”的缺失细节加入 follow-ups。
- 不根据经验猜测需求；不加入已被用户或 spec 明确排除的事项。
- 已记录的 follow-up 视为有意延后的非关键缺口，不报为充分性问题；只有 techspec 与该项矛盾时才报 finding。
- 新增前检查语义重复，重复则不新增。
- 当前 techspec 或 evidence 已覆盖某项时，删除该项；删掉最后一项时删除文件。
- 可以整理措辞，但不得改变事项范围或含义；需要改变范围时保留原项并报 🔴。
- 不得修改 evidence。evidence 与 techspec 冲突时，报 🔴。

## 输出契约

只报告问题；每项使用：

```text
severity | file:line | rule source | why misleading | fix direction
```

- 🔴：需要用户决定或证据修复的语义问题。
- 🟡：有明确、无冲突权威来源时可机械修复的结构或一致性问题。
- 🟢：润色或排版问题。

没有 finding 时明确写 `无发现`。没有行号或规则来源的泛泛建议不报。

单独输出 `Follow-ups 变更`，列出本轮新增、删除或整理的 `FU-*`；它们不是 finding，不带 severity。

## 交接

主 agent 是 techspec 和 evidence 的唯一编辑者。它可修复 🟡 / 🟢 finding；🔴 必须停止并向用户提出选择。主 agent 修完后不重新运行 reviewer，本轮审查到此结束。
